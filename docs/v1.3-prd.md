# NewCar V1.3 工程实施需求文档

日期：2026-06-05

## 0. 版本定位

V1.3 的核心目标是把 NewCar 从“购车信息记录 + 候选对比工具”升级为：

> **证据驱动的主动购车尽调助手。**

产品不再只回答“哪辆车参数更好”，而是持续回答：

1. 这款车是否值得继续观察？
2. 这台具体车源是否有坑？
3. 当前价格、权益、质量证据是否支持下手？
4. 如果不能下手，下一步应该补什么证据、问谁、等什么节点？

本版本必须围绕用户真实购车窗口设计：北京新能源指标于 2026-05-26 下发，最晚应在 2027-05-26 前完成上牌。用户有较长观察期，需要长期跟踪新车上市、二手价格、车型质量和具体车源尽调进度。

## 1. 研究依据与设计假设

### 1.1 内部依据

- 现有产品已具备：总览、用车画像、新车观察、二手车源、候选尽调、单车详情、质量与三电、信息墙、对比、试驾、待关闭风险、商家、AI 分析、懂车帝数据服务。
- V1.2 文档已确认方向：
  - 新车和二手车必须分流；
  - 用车画像必须成为所有刷新、排序、分析的共同基准；
  - 信息墙必须支持截图/照片，并由 AI 提取结构化信息；
  - 三电质量和长期质量必须成为硬指标；
  - 风险必须能被证据关闭，而不是泛泛提示。

### 1.2 外部依据

- 北京小客车指标有效期为 12 个月，不得转让。来源：[北京市小客车数量调控暂行规定](https://www.beijing.gov.cn/zhengce/zhengcefagui/202012/t20201206_2157922.html)。
- 二手车常见纠纷集中在隐瞒维修、事故、泡水、调表、合同承诺不清等问题。来源：[中国质量新闻网汽车投诉报道](https://m.cqn.com.cn/pp/content/2023-05/11/content_8937814.htm)。
- 新能源二手车交易规模增长，跨区域流通增强，异地车源和平台担保车源将持续成为用户决策对象。来源：[人民日报二手车市场报道](https://paper.people.com.cn/rmrb/pad/content/202601/18/content_30133379.html)、[中国汽车流通协会](https://www.cada.cn/Data/info_86_10222.html)。
- GB 38031-2025 电动汽车用动力蓄电池安全强制国标将于 2026-07-01 实施，应作为新车观察和二手车安全评估的重要背景。来源：[中国政府网](https://www.gov.cn/lianbo/bumen/202504/content_7019269.htm)。
- 长期质量应优先参考官方召回/缺陷调查、投诉销量比、第三方质量研究和单车级检测材料。来源：[国家缺陷产品召回技术中心](https://www.samrdprc.org.cn/)、[车质网投诉销量比排行](https://www.12365auto.com/ranking/sales-2026-2-2-110-13-4-0-1-3-0-0-0.shtml)、[J.D. Power 中国新能源汽车新车质量研究](https://china.jdpower.com/zh-hans/press-releases/2026zhongguoxinnengyuanqichexinchezhiliangyanjiu)。

## 2. 目标用户与关键场景

### 2.1 核心用户

北京新能源指标持有人，2 人用车，主要市区通勤，假期高速长途。预算约 30 万，纯电优先，后排需求弱，前排舒适、NVH、底盘、车机、高速 NOA、内饰质感、外观审美权重高。已试驾并认可理想 i6，希望找到类似驾乘体验但价格更合理、风险可控的选择。用户可接受准新二手车，但对事故修复、三电质保、权益转移、商家承诺和价格安全垫非常敏感。

### 2.2 关键任务

1. 保存并持续修正自己的用车画像。
2. 跟踪近期发布和即将上市的新车。
3. 刷新懂车帝等平台上的官方/自营/个人/第三方二手车源。
4. 把重点车型或车源加入候选尽调。
5. 上传截图、检测报告、聊天记录、报价单，让 AI 提取事实并发现风险。
6. 对每台候选车建立三电和长期质量档案。
7. 对每个车源进行商家背调、权益核验和成交前红线检查。
8. 用理想 i6 作为体验标尺做试驾复盘。
9. 根据上市节奏、价格变化和风险关闭情况决定买、等、谈价或放弃。

## 3. 版本目标与非目标

### 3.1 版本目标

V1.3 需要完成五个工程结果：

1. **质量与三电可信数据闭环**：每辆候选车都有车系级质量档案和单车级三电证据状态。
2. **二手车源尽调流水线**：每台具体车源都有阶段、任务、风险、证据、合同承诺和购买门槛。
3. **新车观察时间线**：每个重点新车车型都有上市、改款、权益、试驾、价格和质量事件。
4. **AI 证据工作台**：信息墙支持多图/截图输入、结构化提取、字段回填预览、风险关联和人工确认。
5. **成交前红线检查**：系统能明确告诉用户哪些风险未关闭，是否不建议下订。

### 3.2 非目标

- 不做泛汽车社区。
- 不做完整汽车百科。
- 不追求覆盖所有车型，优先覆盖用户画像命中的重点新能源车型。
- 不用黑盒 AI 生成没有来源的质量分。
- 不让 AI 自动覆盖用户数据，所有核心字段回填必须确认。
- 不把新车车型和二手具体车源混成同一种对象。

## 4. 范围与优先级

### 4.1 P0 范围

1. 质量与三电数据自动获取/刷新。
2. 二手车源加入候选后的尽调任务自动生成。
3. 新车观察时间线和重点车型池。
4. 信息墙 AI 结构化提取与回填确认。
5. 成交前红线检查。
6. AI 任务状态、失败原因和重试机制。
7. 新车/二手刷新严格使用首页用车画像。

### 4.2 P1 范围

1. 商家档案和商家承诺合同化。
2. 试驾脚本和 i6 相似度复盘。
3. 价格历史、目标价和降价观察。
4. 对比页升级为决策摘要。
5. 质量数据源冲突提示。

### 4.3 P2 范围

1. 云端同步和多设备数据备份。
2. 主动提醒和自动定时刷新。
3. 更多垂直信源接入。
4. 报告导出模板升级。

## 5. 核心信息架构

### 5.1 主对象

| 对象 | 定义 | 示例 |
|---|---|---|
| UserProfile | 用户长期购车画像 | 北京、2 人、纯电、30 万、i6 标尺 |
| NewVehicleModel | 新车车型/版本观察对象 | 理想 i6、蔚来 ES6、极氪 7X |
| UsedListing | 一台具体二手车源 | 懂车帝重庆店 22.46 万理想 i6 |
| Candidate | 已进入尽调的候选对象 | 新车候选或二手车源候选 |
| EvidenceItem | 信息墙证据 | 截图、报告、聊天、链接、手写笔记 |
| QualityProfile | 质量与三电档案 | 召回、投诉销量比、SOH、故障码 |
| InvestigationTask | 尽调任务 | 索要 SOH、确认质保、看合同 |
| RiskItem | 风险项 | 三电证据缺失、权益不随车、修复多 |
| VehicleEvent | 新车观察事件 | 上市、权益调整、改款、试驾车到店 |
| SellerProfile | 商家档案 | 懂车帝直营、卡泰驰、第三方车商 |
| AIJob | AI 分析任务 | 信息墙分析、质量刷新、商家背调 |
| PriceSnapshot | 价格快照 | 报价、新车权益价、目标价 |
| DecisionReport | 决策报告 | 可买/可谈/继续等/放弃 |

### 5.2 对象边界

- NewVehicleModel 是“车型/版本”，没有单车车况。
- UsedListing 是“一台车源”，必须有城市、卖方、里程、上牌时间、过户、检测/保障信息。
- Candidate 可以引用 NewVehicleModel 或 UsedListing，但必须保留对象类型。
- EvidenceItem 不能只是备注，它必须能关联 Candidate、RiskItem、QualityProfile、SellerProfile 或 PriceSnapshot。
- QualityProfile 需要区分“车系级质量线索”和“单车级质量证据”。

## 6. 数据模型要求

### 6.1 UserProfile

必填字段：

- id
- updatedAt
- city
- licenseDeadline
- budgetMin
- budgetMax
- energyPreference
- passengerScenario
- usageScenario
- priorityWeights
- benchmarkVehicle
- excludedPreferences
- notes

工程要求：

- 每次保存画像时生成 profileVersion。
- 新车刷新、二手车刷新、候选排序、AI 分析都必须记录使用的 profileSnapshotId。
- 刷新结果中要展示“本次使用画像摘要”。

验收标准：

- 用户修改“只看纯电”后，二手车刷新结果不得出现油车。
- 用户修改预算后，新车和二手车排序原因必须重新计算。
- 用户可在画像页看到最近 5 次画像变化。

### 6.2 Candidate

必填字段：

- id
- objectType: `new_model | used_listing | manual`
- name
- trim
- city
- source
- sellerId
- price
- newPrice
- targetPrice
- range
- batteryOwnership
- batterySize
- energyType
- status
- stage
- profileSnapshotId
- qualityProfileId
- investigationTaskIds
- riskItemIds
- evidenceIds
- priceSnapshotIds
- createdAt
- updatedAt

stage 枚举：

- discovered
- observing
- due_diligence
- test_drive
- negotiating
- ready_to_buy
- rejected
- purchased

验收标准：

- 候选列表必须能按 objectType 分组。
- 移出候选后，列表页、详情页、对比页、风险页都不能继续显示该候选。
- 每个候选详情页必须显示 stage、下一步任务和未关闭风险数。

### 6.3 QualityProfile

字段：

- id
- candidateId
- vehicleSeriesName
- modelYear
- confidenceLevel: `high | medium | low | unknown`
- threeElectricRisk: `low | medium | high | unknown`
- evidenceCompleteness: 0-100
- complaintSalesRatio
- complaintSalesRatioSource
- threeElectricComplaintShare
- recallCount
- defectInvestigationCount
- jdPowerOrThirdPartySummary
- ownerReputationSummary
- batterySoh
- maintenanceStatus
- troubleCodeStatus
- warrantyStatus
- batteryRepairStatus
- gb38031Status
- sources
- missingItems
- questions
- updatedAt

source 可信度等级：

- A：官方召回、缺陷调查、品牌公告、法规标准。
- B：投诉销量比、投诉列表、公开销量口径。
- C：第三方质量研究、行业报告。
- D：车主口碑、论坛、媒体长期测试。
- S：单车级证据，如 SOH、维保、故障码、检测报告。

验收标准：

- 缺少 SOH、维保、故障码或三电质保时，二手电车必须生成待关闭风险。
- 没有来源的数据不能展示为“有数据”，只能展示为“待核验线索”或“缺失”。
- 质量模块必须展示更新时间和来源链接。
- AI 生成的质量结论必须区分“事实”“线索”“推断”。

### 6.4 EvidenceItem

字段：

- id
- candidateId

- rawText
- attachments
- sourceUrl
- extractedFields
- linkedRiskIds
- linkedQualitySignalIds
- confidence

- analysisResult

验收标准：

- 用户可逐项选择应用字段，而不是一键覆盖全部。
- 已应用字段需要记录来源 evidenceId。

- dueDate

- 二手车加入候选后自动生成默认尽调任务。

- 同一车型事件需要去重，不能出现重复卡片。

## 7. 功能需求

### FR-1 用车画像与画像快照

用户故事：

作为用户，我希望系统记住我的真实购车偏好，并在每次找车、排序和分析时明确使用这份画像，这样我知道推荐不是泛泛而来。

功能要求：

1. 首页保留“理解需求并找车”入口。
2. 画像页支持编辑、保存、预览、历史版本。
3. 新车观察、二手车源、候选尽调、质量刷新都必须使用当前默认画像。
4. 每次刷新结果顶部展示画像摘要。
5. 画像变化后，已存在候选不自动删除，但排序和推荐理由需要重新计算。

验收标准：

- 修改能源偏好为纯电后，二手刷新不得返回燃油车。
- 修改预算后，超预算候选需要标记“超预算但可观察”或降权。
- 刷新日志中能看到本次 profileSnapshotId。

### FR-2 新车观察

用户故事：

作为用户，我希望看到近期发布、即将发布和热门新能源车型，并知道哪些车型值得等、值得试驾或可以放弃。

功能要求：

1. 支持刷新新车观察池。
2. 数据来源包括：
   - 懂车帝车型页/资讯；
   - 行业发布资讯；
   - 用户重点车型池；
   - 本地已有候选。
3. 结果必须按画像过滤和排序。
4. 同一车型需要按规范化名称去重。
5. 每张卡片展示：
   - 车型名；
   - 发布时间或预计上市时间；
   - 价格区间；
   - 续航/电池；
   - 能源形式；
   - 适配度；
   - 为什么值得看；
   - 主要不确定性；
   - 加入新车候选；
   - 打开车型页；
   - 查看上市资讯。
6. 车型详情页展示 VehicleEvent 时间线。

验收标准：

- 小米 YU7 等同一车型不得在列表中重复出现。
- 纯电画像下，增程/插混可以作为“扩展观察”，但不能排在纯电候选前，且必须标注原因。
- 刷新失败时展示数据源失败原因和上次成功数据。

### FR-3 二手车源

用户故事：

作为用户，我希望从懂车帝官方/自营/个人/第三方车源中筛选真正适合我的二手新能源车，而不是混进油车或不相关车源。

功能要求：

1. 二手车源刷新必须使用首页画像。
2. 支持按城市、车源类型、能源类型、预算、里程、上牌时间、卖家类型筛选。
3. 默认城市包含北京、重庆、武汉，可扩展上海、石家庄等用户曾关注城市。
4. 车源类型必须明确：
   - 懂车帝官方直营；
   - 懂车帝自营；
   - 个人直卖；
   - 第三方商家；
   - 品牌官方认证；
   - 未知。
5. 每张卡片展示：
   - 车源标题；
   - 报价；
   - 新车参考价；
   - 上牌时间；
   - 里程；
   - 过户次数；
   - 城市；
   - 卖方类型；
   - 保障口径；
   - 初步风险；
   - 加入候选尽调；
   - 打开外部车源。
6. 加入候选后自动创建 UsedListing Candidate 和默认尽调任务。

验收标准：

- 纯电画像下不出现油车。
- 车源加入候选后，详情页必须能打开原始外部链接。
- 外部链接不能只打开懂车帝首页，必须尽可能打开对应详情页；如果受平台限制，显示备用链接和车源 ID。

### FR-4 候选尽调

用户故事：

作为用户，我希望候选库不是收藏夹，而是能清楚告诉我每台车处于什么阶段、还缺什么证据、下一步该做什么。

功能要求：

1. 候选库支持列表视图和阶段视图。
2. 阶段包括：
   - 观察中；
   - 待补证；
   - 待试驾；
   - 待谈价；
   - 可成交；
   - 已放弃。
3. 候选卡片展示：
   - 类型；
   - 价格；
   - 风险等级；
   - 质量可信度；
   - 未关闭风险数；
   - 下一步任务；
   - 最近更新时间。
4. 单车详情页桌面端采用主内容 + 右侧决策栏布局。
5. 移动端采用顶部结论卡 + 分段内容。
6. 移出候选必须同步清理关联视图。

验收标准：

- PC 详情页图片、摘要、右侧风险栏不能重叠。
- 列表页到详情页返回时保留滚动位置。
- 移出候选后，对比、风险、试驾、商家关联中不再出现。

### FR-5 质量与三电可信评估

用户故事：

作为用户，我希望知道一款电车的三电和长期质量到底稳不稳，并清楚哪些结论有证据、哪些只是线索。

功能要求：

1. 候选详情中保留独立“质量与三电”模块。
2. 提供“AI 刷新质量数据”按钮。
3. 刷新流程需要检索并结构化：
   - 官方召回；
   - 缺陷调查；
   - 车质网投诉销量比；
   - 三电相关投诉关键词；
   - 第三方质量研究；
   - 车主口碑；
   - GB 38031-2025 相关状态；
   - 单车 SOH、维保、故障码、三电质保。
4. 质量结果分为：
   - 车系级质量档案；
   - 单车级质量证据；
   - 缺失证据；
   - 需要问商家的问题。
5. 展示证据可信度等级。
6. 数据不足时显示“未知风险”，不得默认低风险。

验收标准：

- 用户点击刷新后能看到任务状态：排队、检索中、分析中、完成或失败。
- 结果中每个关键数字必须带来源或标记为“待核验”。
- SOH 为 0 或空时，不得显示“有证据”；必须显示“SOH 缺失/待核验”。
- 高风险质量结论必须自动生成待关闭风险。

### FR-6 信息墙 AI 证据工作台

用户故事：

作为用户，我希望把手机截图、检测报告、报价单、聊天记录直接丢进来，由 AI 帮我提取事实、发现矛盾并更新候选信息。

功能要求：

1. 支持文本、链接、图片、截图、报告上传。
2. 支持一次上传多张图片。
3. 上传后创建 EvidenceItem。
4. AI 分析输出：
   - 识别到的原始事实；
   - 可回填字段；
   - 新风险；
   - 需要追问的问题；
   - 关联质量数据；
   - 关联商家信息；
   - 置信度。
5. AI 回填必须进入确认面板。
6. 用户可逐项应用、忽略或编辑。
7. 应用后记录字段来源。

验收标准：

- 大图过大时给出明确提示和压缩/分批建议。
- AI 失败时不丢失原始证据。
- 已应用字段可查看来源证据。
- 同一证据可重新分析。

### FR-7 商家档案

用户故事：

作为用户，我希望知道卖车的人或店是否可靠，以及他们说的保障能否写进合同。

功能要求：

1. 建立 SellerProfile。
2. 车源加入候选时自动创建或关联商家。
3. 商家页展示：
   - 商家名称；
   - 类型；
   - 城市；
   - 平台身份；
   - 关联车源；
   - 承诺清单；
   - 风险记录；
   - 背调来源；
   - 待确认问题。
4. 提供“AI 背调商家”按钮。
5. 商家承诺可转成合同核验任务。

验收标准：

- 同一商家不同车源能聚合在同一个商家档案。
- “官方认证”“平台担保”“车商自称认证”必须分开标注。
- 未写入合同的关键承诺不能算风险关闭。

### FR-8 价格与节奏观察

用户故事：

作为用户，我希望系统帮助我判断现在买是否划算，还是应该等降价、等改款或等更多二手车源。

功能要求：

1. 每个候选支持 priceSnapshot。
2. 记录：
   - 当前报价；
   - 新车参考价；
   - 优惠后新车价；
   - 落地成本；
   - 电池租赁成本；
   - 运输/上牌/保险；
   - 目标价；
   - 历史报价。
3. 支持“记录当前报价”。
4. 支持“到价提醒”状态。
5. 对新车增加上市/权益/改款时间线。
6. 对二手车增加报价安全垫判断。

验收标准：

- 二手价接近新车权益后价格时，系统提示“二手优势不足”。
- BaaS 车必须展示 1 年、3 年、5 年持有成本。
- 用户可看到目标价差距。

### FR-9 试驾与 i6 体验标尺

用户故事：

作为用户，我希望用理想 i6 作为标尺，记录每台车是否真的接近我认可的驾乘体验。

功能要求：

1. 试驾前生成任务脚本：
   - 前排座椅；
   - 底盘滤震；
   - 静音；
   - 车机；
   - 高速 NOA；
   - 转向和刹车；
   - 空间和视野；
   - 内饰质感。
2. 试驾后记录评分和文字证据。
3. 自动生成 i6 相似度说明。
4. 试驾记录可作为 EvidenceItem。

验收标准：

- 每个评分必须能填写文字理由。
- 对比页能展示“相对 i6 更好/接近/不如”的项目。

### FR-10 决策报告与成交前红线检查

用户故事：

作为用户，我希望在准备下订前，系统能明确告诉我是否还有不能放过的风险。

功能要求：

1. 候选详情提供“生成决策报告”。
2. 报告包含：
   - 当前结论；
   - 推荐动作；
   - 适配画像；
   - 成本；
   - 质量与三电；
   - 风险；
   - 商家；
   - 证据完整度；
   - 未关闭红线；
   - 下一步清单。
3. 红线项包括：
   - SOH 缺失；
   - 三电质保不清；
   - 维修/出险/事故不清；
   - 检测报告缺失或不完整；
   - 商家承诺未进合同；
   - 价格没有安全垫；
   - 权益转移不清；
   - 电池产权/BaaS 成本不清；
   - 车源链接或状态无法复核。
4. 红线未关闭时，不允许生成“建议购买”结论，只能输出“可继续谈/需补证/建议放弃”。

验收标准：

- 报告中的每条结论都有证据或明确标注为推断。
- 红线未关闭时，主结论必须阻断。
- 报告可导出为 Markdown/JSON。

### FR-11 AI 任务中心与模型容错

用户故事：

作为用户，我希望 AI 能稳定工作；即使失败，也能知道失败原因，并且可以重试或使用备用模型。

功能要求：

1. 所有 AI 操作抽象为 AIJob。
2. AIJob 类型：
   - profile_interpretation
   - newcar_refresh
   - usedcar_ranking
   - evidence_analysis
   - quality_refresh
   - seller_research
   - risk_analysis
   - decision_report
3. AIJob 状态：
   - queued
   - running
   - success
   - failed
   - fallback_used
   - user_confirmed
4. 服务端保留 provider 链：
   - 默认 Gemini；
   - Gemini 失败后可使用 DeepSeek 或本地规则；
   - 前端不暴露 API Key。
5. 失败原因必须可读：
   - key_missing
   - quota_exceeded
   - network_error
   - invalid_response
   - source_blocked
   - parse_failed
6. AI 输出必须经过 schema 校验。

验收标准：

- 不再只显示“Gemini 暂不可用”，必须显示具体原因和下一步。
- 用户可对失败任务点击重试。
- 使用备用模型时，结果中标注 provider。
- 本地规则兜底结果必须明显标记，不得伪装为 AI 结论。

## 9. 页面与交互要求

### 9.1 总览

必须回答“今天该做什么”。

模块：

- 当前画像摘要；
- 指标到期倒计时；
- 重点候选；
- 待关闭红线；
- 到价/改款/权益提醒；
- 最近 AI 任务；
- 推荐下一步。

验收标准：

- 用户进入首页 10 秒内能看到最重要的 3 个待办。
- 总览页提供“重新分析当前候选”和“刷新质量/车源”的入口，但不堆满按钮。

### 9.2 新车观察

必须明确这是车型观察，不是车源。

交互：

- 顶部画像摘要；
- 重点车型池；
- 刷新按钮；
- 新车卡片；
- 车型事件时间线；
- 加入新车候选。

验收标准：

- 重复车型合并；
- 同车型不同版本可在详情里展开；
- 移动端卡片按钮不换行挤压。

### 9.3 二手车源

必须明确这是具体车源。

交互：

- 顶部画像摘要和筛选；
- 来源说明；
- 车源卡片；
- 初步风险；
- 加入候选尽调；
- 外部车源链接；
- 车源失效/下架状态。

验收标准：

- 油车过滤准确；

### 9.4 候选尽调

交互：

- 列表页展示所有候选；
- 支持分组：新车候选、二手车源、手动候选；
- 支持阶段看板；
- 点击进入详情；
- 返回保留滚动位置；
- PC 详情页左右布局稳定；
- 移动端详情页分段导航。

验收标准：

- 当前截图中出现过的 PC 详情布局重叠问题不得复现。
- 图片必须保持比例，不撑破卡片。
- 详情页右侧决策栏在窄屏下下移。

### 9.5 质量与三电

交互：

- 顶部结论卡：质量可信度、三电风险、证据完整度。
- 下方证据卡分组：
  - 官方召回/缺陷；
  - 投诉销量比；
  - 第三方质量研究；
  - 车主口碑；
  - 单车证据。
- 每张卡显示状态：有数据、待核验、缺失、冲突。
- 提供 AI 刷新和问商家清单。

验收标准：

- 卡片布局不得横向溢出。
- 数据缺失时显示缺失原因和补证动作。

### 9.6 信息墙

交互：

- 上传区支持拖拽、选择图片、粘贴文本、粘贴链接。

验收标准：

- 图片上传后有预览。
- 多图不会导致页面卡死。
- AI 分析失败后可重试。

## 10. 风险规则

### 10.1 红线风险

以下风险必须阻断“建议购买”：

- 二手电车缺少 SOH 或等效电池健康证据。
- 三电质保是否随车不清。
- 检测报告缺失或关键页缺失。
- 出险/维修/事故记录不清。
- 过户、抵押、营运属性不清。
- 商家核心承诺未写入合同。
- BaaS、买断、智驾订阅、首任权益转移不清。
- 价格与新车权益价相比没有安全垫。

### 10.2 中风险

- 新车刚发布，首批质量未知。
- 即将改款或权益可能调整。
- 异地车源，复检和运输成本高。
- 商家身份不够清晰。
- 车源图片、配置、标题存在不一致。

### 10.3 低风险

- 有明确证据支持，且不影响交易安全。
- 用户已明确接受并记录理由。

## 11. AI 输出规范

AI 结论必须遵循：

1. 不得伪造来源。
2. 不得把线索写成事实。
3. 不得在红线未关闭时输出“建议购买”。
4. 不得自动覆盖用户字段。
5. 必须输出：
   - facts；
   - assumptions；
   - risks；
   - fieldPatches；
   - questions；
   - sources；
   - confidence；
   - provider。

质量数据尤其要区分：

- 官方确认；
- 公开投诉；
- 第三方研究；
- 车主口碑；
- 单车报告；
- AI 推断。

## 12. 可用性与视觉验收

### 12.1 桌面端

- 主内容最大宽度合理，避免卡片横向挤压。
- 详情页图片区域必须设定稳定宽高和 object-fit。
- 右侧决策栏固定在可读宽度，不能压住主内容。
- 卡片内中文长文本必须换行。
- 质量证据卡采用响应式 grid，最小列宽不低于 240px。

### 12.2 移动端

- 底部导航不超过 5 个主入口。
- 新车/二手可合并到“发现”，候选/风险/详情合并到“尽调”。
- 主要按钮高度不低于 44px。
- 上传截图流程必须在手机浏览器中可用。
- Tab 切换保留滚动位置，不强制跳到顶部。

### 12.3 空状态

所有空状态必须告诉用户下一步：

- 没有质量数据：点击 AI 刷新，或上传报告。
- 没有二手车源：调整城市/预算/能源筛选。
- 没有证据：上传截图、报价、报告或聊天记录。
- 没有商家信息：从车源添加或手动输入。

## 13. 数据可靠性策略

### 13.1 来源优先级

1. 单车级证据：SOH、维保、故障码、检测报告、合同。
2. 官方来源：召回、缺陷调查、品牌公告、法规。
3. 结构化投诉与销量数据：投诉销量比、投诉关键词。
4. 第三方质量研究。
5. 车主口碑、媒体评测、论坛。

### 13.2 冲突处理

当数据冲突时：

- 不覆盖旧数据；
- 创建“证据冲突”风险；
- 展示冲突来源；
- 要求用户确认采用哪个来源；
- 记录决策原因。

### 13.3 数据过期

默认过期规则：

- 新车价格/权益：14 天过期。
- 二手车源状态：7 天过期。
- 质量与投诉数据：30 天过期。
- 商家背调：60 天过期。
- 单车检测报告：除非车源状态变化，否则不过期，但需要标注报告日期。

## 14. 指标与验收

### 14.1 功能完成指标

- 关键纯函数有测试覆盖：
  - 新车去重；

## 16. 技术注意事项

1. 当前 `app.js` 已较大，新增能力应优先抽象为清晰的函数区域或逐步拆分模块，避免继续扩大单文件复杂度。
2. 前端不得保存明文 AI API Key。
3. AI 服务失败必须可诊断，不再只给笼统 toast。
4. 数据结构变更需要兼容 localStorage 旧数据。
5. 导入/导出 JSON 要包含 schemaVersion。
6. 所有外部链接都要支持 sourceUrl 和 fallbackUrl。
7. 任何自动化抓取都要尊重目标网站访问限制；无法抓取时保留手动录入和截图上传路径。

## 17. 开放问题

1. V1.3 是否继续保持纯前端 + Node 服务，还是引入轻量云端存储？
2. AI provider 链是否确定为 Gemini 优先、DeepSeek 备用、本地规则兜底？
3. 质量数据中车质网投诉销量比是否允许用户手动录入并由 AI 校验？
4. 是否需要主动提醒能力，例如每天自动刷新重点车源价格？
5. 是否需要把“新车观察”和“二手车源”在移动端合并为一个“发现”入口？

## 18. Definition of Done

V1.3 可认为完成，当且仅当：

1. 用户打开总览能看到当前最重要的候选、风险和下一步。
2. 新车观察不重复、能显示时间线、能按画像排序。
3. 二手车源不会在纯电画像下混入油车。
4. 任意二手电车加入候选后会自动生成质量、车况、权益、商家、合同尽调任务。
5. 质量与三电模块能区分有数据、缺失、待核验、冲突。
6. 信息墙能上传图片并通过 AI 生成待确认回填。
7. 红线风险未关闭时，决策报告不会建议购买。
8. PC 和移动端核心页面没有布局重叠、横向溢出和按钮挤压。
9. 关键逻辑有测试覆盖并通过。
10. 文档、导出 JSON 和本地旧数据迁移均可用。
